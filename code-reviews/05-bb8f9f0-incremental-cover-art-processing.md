# Code Review: bb8f9f0 — feat: incremental cover art processing

## Summary

This commit adds a parallel tracking mechanism (`cover_tracking` SQLite table + five functions) intended to let a future scan skip re-fetching cover art for files whose cover was already processed and haven't changed since. It closely mirrors the existing `file_mtime_tracking` machinery added in d57f62e, but is purely additive: nothing in `update_music_metadata.sh`, `main()`, or the existing `find_incomplete()` flow calls any of the five new functions. The code itself is small, uses parameterized SQL correctly, and is reasonably tested in isolation, but it duplicates the older mtime-tracking pattern almost verbatim instead of factoring out a shared helper, silently drops the `num_workers` parameter it advertises, and introduces a `cover_status` column that is written but never read back anywhere (including in tests). Because it is genuinely unwired at this point in the series, none of this is user-visible yet, but several of the design choices (write-only status column, per-file connection churn in `mark_cover_processed`, mtime-only staleness check) will need to be revisited before integration — verdict: acceptable as a scaffolding commit, but flagged as unverified-in-practice and carrying reuse/design debt that should be paid down before it's wired into the real scan path.

## Files Changed

- `scan_incomplete.py` — adds `init_cover_db()`, `get_cover_mtime()`, `update_cover_tracking()`, `find_files_needing_cover_update()`, `mark_cover_processed()`, and a docstring line advertising "Incremental cover processing"; no call sites added, `main()` is untouched.
- `tests/test_scan_incomplete.py` — adds 4 new tests (`test_init_cover_db`, `test_cover_tracking_get_and_update`, `test_find_files_needing_cover_update`, `test_mark_cover_processed`) exercising the new functions in isolation.

## Findings

### Critical

None found.

### High

### Medium

1. **`num_workers` parameter is accepted but silently ignored** — `scan_incomplete.py:367` (`find_files_needing_cover_update(music_dir, cover_db_path, num_workers=None)`). Unlike `find_incomplete()` (line 292), which actually uses `num_workers` to size a `ThreadPoolExecutor`, this function walks the tree and does one sequential `os.path.getmtime()` + one sequential SQL `SELECT` per file (lines 393-400) with no parallelism at all. A caller reading the signature next to `find_incomplete`'s would reasonably assume parity (same optional param, same meaning) and could pass `num_workers=16` expecting a speedup that never happens. For a large library this will be noticeably slower than `find_incomplete`'s equivalent scan since it does N sequential round-trips against SQLite instead of loading tracked mtimes once. Fix: either drop the unused parameter now (it's dead until the function actually parallelizes) or implement the same batched-connection-per-thread pattern used in `find_incomplete`/`_check_file_with_retry`.

2. **`cover_status` is write-only — no getter exists, and no test asserts its stored value** — `scan_incomplete.py:148-155` (`get_cover_mtime`) only ever selects the `mtime` column; there is no `get_cover_status()` and no query anywhere reads the `cover_status` column back. `update_cover_tracking()` (line 158-167) happily accepts and stores it, and `test_cover_tracking_get_and_update` (tests/test_scan_incomplete.py:496-514) passes `cover_status="success"` but only asserts `get_cover_mtime(...) == mtime` — the status value is never checked to have round-tripped correctly. Combined with finding #3 below, this means the column exists in the schema and in the function signatures purely speculatively; nothing in the commit demonstrates it behaves as intended, which is exactly the "can't be verified with real usage" risk called out for the unwired functions, but here it applies even within the isolated unit tests.

3. **Staleness check is mtime-only and ignores `cover_status`, so a previously-failed fetch can never be retried without an unrelated file modification** — `scan_incomplete.py:393-400`. `find_files_needing_cover_update()` decides "needs update" purely from `tracked_cover_mtime is None or current_mtime != tracked_cover_mtime`. If a prior run recorded `cover_status="not_found"` or `"error"` (a plausible future value, given `mark_cover_processed` takes an arbitrary `cover_status` string), the file is nonetheless treated as "fully processed" and will be skipped on every subsequent run until its mtime changes for an unrelated reason (e.g., a tag edit). Once this is wired into the real fetch path, a transient Cover Art Archive outage or a genuinely cover-less release would get permanently blacklisted from re-fetch attempts. This isn't a bug yet (nothing calls the function), but the schema/logic combination bakes in this gap now, so it should be designed correctly before integration — e.g., only treat `cover_status == "success"` as "no need to recheck," or track failures with their own backoff/blacklist similar to `error_tracking`.

4. **`mark_cover_processed()` opens and closes a fresh SQLite connection per file, unlike the batching pattern the codebase already established for exactly this concern** — `scan_incomplete.py:406-417`. `find_incomplete()` explicitly avoids per-file connections during parallel work and instead batches all mtime writes into a single connection after the `ThreadPoolExecutor` completes (see the comment "Batch update mtime tracking (once per batch to avoid thread contention)" at `scan_incomplete.py:330` and the batched write loop at lines 354-362). `mark_cover_processed`, by contrast, is written to be called once per file with its own `init_cover_db()` → `INSERT OR REPLACE` → `commit()` → `close()` cycle. If this is invoked per-file inside a future threaded cover-fetch loop (the obvious integration point, mirroring `_check_file_with_retry`), it reintroduces the exact multi-connection contention risk the mtime-tracking code was already careful to avoid, and each call pays SQLite connection/commit overhead individually. Should be redesigned to accept a batch of `(filepath, status)` results (or an open connection) the way `update_mtime_tracking` is batched.

### Low / Nitpicks

1. **Significant copy-paste duplication vs. the d57f62e mtime-tracking code, with no shared helper extracted.** `init_cover_db` (lines 47-59) is structurally identical to `init_error_db`/`init_mtime_db` (lines 30-44, 114-125) apart from the table name/columns; `get_cover_mtime`/`update_cover_tracking` (lines 148-167) are line-for-line the same shape as `get_tracked_mtime`/`update_mtime_tracking` (lines 128-145), down to variable names (`now = time.time()`, `INSERT OR REPLACE`, `row[0] if row else None`). A generic `_init_kv_db(db_path, table, columns)` / `_get_tracked_value(conn, table, filepath, column)` pair (or a tiny wrapper class) would have removed ~40 lines of near-identical code and made the "one more tracking table" pattern (which this repo now has three of: error, mtime, cover) trivial to extend safely in the future. Worth refactoring before a fourth copy appears.

2. **`find_files_needing_cover_update`'s "no `cover_db_path`" branch duplicates the `os.walk` + extension-filter loop that already exists in `find_incomplete`** (`scan_incomplete.py:373-382` vs. `scan_incomplete.py:310-317`), instead of calling a shared "collect audio files" helper. Same root cause as finding #1 above (no shared file-enumeration helper), just a second instance of it.

3. **Docstring vs. implementation mismatch**: `find_files_needing_cover_update`'s docstring (`scan_incomplete.py:368-370`) says "Returns `[filepath, ...]` of files whose cover art should be re-fetched," but doesn't mention that when `cover_db_path` is falsy it returns *every* audio file unconditionally (line 372-382) rather than "files needing update" in any incremental sense — the no-DB branch is really "list all audio files," which is a different contract worth documenting explicitly (mirrors a similar implicit behavior in `find_incomplete` when `mtime_db_path` is `None`, so at least it's a consistent convention, but neither docstring calls it out).

4. **README not updated to reflect that foundational work has started.** The README's "Open items / possible next steps" section already lists "Incremental cover art fetching (only re-fetch covers for recently modified files)" (README.md, under `## Open items / possible next steps`) as an outstanding item. This commit begins exactly that work but does not touch the README — the open-items entry is now stale/misleading (it reads as "not started" when foundation code already exists). Minor, but worth a one-line update or an explicit "in progress" note in a commit that explicitly calls itself "foundation for future optimization."

5. **Filepaths are stored as raw strings without normalization** (`scan_incomplete.py:158-167`, `393-403`), matching the pre-existing mtime-tracking behavior. Not a regression introduced by this commit, but worth noting: the same physical file reached via two different path spellings (symlink, trailing slash, relative vs. absolute) will create two independent `cover_tracking` rows. Since this is inherited from the existing pattern rather than new in this diff, it is listed here for completeness rather than as a fault of this commit.

6. **Unused-code / integration-risk note (as requested):** `init_cover_db`, `get_cover_mtime`, `update_cover_tracking`, `find_files_needing_cover_update`, and `mark_cover_processed` are exported from `scan_incomplete.py` but have zero call sites in `update_music_metadata.sh` or in `main()` at this commit (verified via `git show bb8f9f0:update_music_metadata.sh | grep -n cover` → no matches, and `main()` at lines 420-434 only forwards `mtime_db`/`error_db`/`num_workers`, no `cover_db`). This is consistent with the commit message's own framing ("foundation for future optimization," "not yet wired into the main scan flow") and is not penalized as a defect, but it does mean none of the findings above have been exercised by a real caller yet — they are unverified in practice and should be re-reviewed once integration happens.

## Test Coverage Assessment

The four new tests each cover one function in isolation and, taken together, do exercise the core "unseen → tracked → mtime-changed → detected" matrix reasonably well:

- `test_init_cover_db` (tests/test_scan_incomplete.py:481-494) — schema creation only.
- `test_cover_tracking_get_and_update` (496-514) — get/update round-trip for `mtime`, but (per Medium finding #2) never asserts `cover_status` was stored correctly, even though it's passed in.
- `test_find_files_needing_cover_update` (517-556) — the most substantive test: seeds `cover_tracking` directly via `update_cover_tracking` for an unchanged file and a to-be-modified file, leaves a third file untracked, then calls `find_files_needing_cover_update` once and asserts the three expected outcomes. This is good, but it is not a true end-to-end "process → mark → recheck → skip" sequence — it seeds state with the low-level `update_cover_tracking` API rather than driving the sequence through the public functions a real caller would use (`find_files_needing_cover_update` → simulate processing → `mark_cover_processed` → `find_files_needing_cover_update` again → assert the file is now excluded). That gap matters here specifically because `mark_cover_processed` and `find_files_needing_cover_update` are the two functions meant to be chained together once wired in, and no test proves they actually compose correctly (e.g., that the mtime `mark_cover_processed` records via `os.path.getmtime(filepath)` matches what a subsequent `find_files_needing_cover_update` call will read for the same file).
- `test_mark_cover_processed` (559-580) — only asserts `get_cover_mtime(...)` is not `None` after marking; it doesn't verify the recorded mtime equals the file's actual mtime, doesn't verify `cover_status` was stored, and critically doesn't chain into `find_files_needing_cover_update` to confirm the marked file is subsequently skipped.

Net effect: the individual units are covered, but the realistic operational sequence (scan finds file → cover gets fetched/embedded → `mark_cover_processed` records it → next scan's `find_files_needing_cover_update` correctly excludes it) is never exercised end-to-end through the public API. Given this is the entire point of the feature, a single integration-style test chaining these calls would meaningfully raise confidence and should be added either in this commit or the one that wires the functions in.

## Positive Notes

- SQL is fully parameterized throughout (`?` placeholders in every query in `init_cover_db`, `get_cover_mtime`, `update_cover_tracking`) — no string-formatted SQL, no injection risk.
- `OSError` is caught around `os.path.getmtime()` in both `find_files_needing_cover_update` (line 393-400) and `mark_cover_processed` (line 411-415), consistent with the defensive style already used for the mtime-tracking code, so a file that disappears mid-scan or a permission error won't crash the whole run.
- `mark_cover_processed` and `find_files_needing_cover_update` both no-op gracefully when `cover_db_path` is falsy (lines 372, 408-409), matching the existing optional-DB convention used by `mtime_db_path`/`error_db_path`, which keeps the new feature backward-compatible/opt-in by construction.
- Commit message is honest and well-scoped: it explicitly says this is a "foundation," names what's "not yet wired," and states the future integration point — good commit hygiene for a multi-commit incremental feature series.
- New tests do use real temp files and real `os.path.getmtime()` values (via `tmp_path`) rather than mocking mtimes outright, which is a reasonably faithful test setup for the one integration-style test that does exist (`test_find_files_needing_cover_update`).

## Recommendations

1. Before wiring these functions into the real scan/fetch flow, decide how `cover_status` failures interact with the mtime-only staleness check (Medium #3) — otherwise failed fetches will silently never retry.
2. Add a `get_cover_status()` accessor and a test that actually asserts a stored `cover_status` value round-trips (Medium #2).
3. Either implement real parallelism in `find_files_needing_cover_update` or drop the unused `num_workers` parameter until it's implemented (Medium #1).
4. Redesign `mark_cover_processed` to support batched writes (single connection, multiple records) before it's called per-file from a threaded fetch loop (Medium #4).
5. Extract a shared "SQLite key/value tracking table" helper to de-duplicate `init_error_db`/`init_mtime_db`/`init_cover_db` and their paired get/update functions (Low #1) — do this now, before a fourth tracking table is added.
6. Add one integration-style test that chains `find_files_needing_cover_update` → `mark_cover_processed` → `find_files_needing_cover_update` again to prove the intended workflow actually composes.
7. Update the README's "Open items" list to reflect that incremental cover tracking has started, or leave a TODO note pointing at this commit.
